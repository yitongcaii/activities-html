  • git 提交用 git add <具体文件> 而非 git add -A：避免误带工作区遗留大文件（如 ppt-gallery-assets ~35MB）。
Git LFS 指针文件认知（适用于含二进制资源的仓库）
  • 走 Git LFS 的文件，clone / 网页看到每个文件仅 ~130 字节、内容是 version https://git-lfs.github.com/... 的指针，非真实内容。用户说"文件丢了 / 空的"先查是否 LFS 指针，主动说明这是正常机制；验证用 curl -I media.githubusercontent.com/... 看 Content-Length 是否真实大小。
⚠️ 生成产物维护铁律（通用，2026-08-05 固化）
  • 适用范围：任何"脚本 / 工具 / 模板生成产物"的场景——构建脚本出 HTML、自动化报表出数据文件、模板渲染出文档、代码生成器等。不限于某个项目或某份看板。
  • 根治铁律：改动一律改源（脚本 / 模板 / 配置 / 数据源），不碰产物（生成的 HTML / 数据文件 / 输出文档 / 生成代码）。
  • 根因：手工改终产物 ↔ 重跑 / 重生成脚本本质冲突——① 重跑会覆盖手工改动（白改）；② 手工改让产物与源码漂移失准，下次重跑又回退，且改动无法追溯、无法复用。
  • 验收：需求落地后确认改动在源码、产物由脚本重新生成（不手动 edit 产物文件）。例外：仅当产物无对应源码 / 一次性手工产物且不重跑时，才允许直接改产物。
  • （博闻看板 build_dashboard2.py 即此铁律的典型案例，见项目级）
⚠️ 批量编辑 / 删除任务防漏验收铁律（2026-08-05 漏删返工后固化）

根因：长串"删掉：A… B…"指令里，夹在正文中、外观不像 UI 标签的"编辑批注"（"替代老套的…""〔XX备选〕可加…""上一句即范例"）易被误判为"修改说明"只执行显眼部分就收工 → 返工。

铁律：

  • 1. 先拆逐条 checklist，每条 = 一个可验收项。
  • 2. 每条执行后必须有验收证据（grep 关键词 / 对照），全绿才提交，不靠"感觉做完了"。
  • 3. 做完反向扫描：用户列的所有删除项是否还有残留（不止查"我删的那个"）。
  • 4. 识别"编辑批注"特征默认删：以"替代 / 可加 / 范例 / 进阶玩法 / 直接改"开头、带"〔XX备选〕"、或"（例：…）"——除非用户明确说保留。
  • 5. 整文件通读 diff 或关键段落再收工，确认无"像注释但非正文"的东西漏网。
  • 6. 凡整文件替换 / 重构，必须复查"页脚 / 统一装饰"没被覆盖丢。
